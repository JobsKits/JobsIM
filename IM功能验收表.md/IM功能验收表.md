## 🔥 <font id=前言>前言</font>

本台账依据 [需求总纲](../IM需求明细表.md/IM需求明细表.md)、[前端架构表](../IM前端架构表.md/IM前端架构表.md) 与 [后端架构表](../IM后端架构表.md/IM后端架构表.md) 建立，当前设计基线日期为 **2026年10月8日**。它用于逐项记录实现后的验收结果，不是已实现功能清单。覆盖 **102 项前端功能、36 项后端能力、12 项平台安全要求、58 项链路场景和 35 项架构交付要求，共 243 项**，全部初始化为“未验收”。

“验收对象”是便于扫读的摘要，完整要求、权限、异常、参数和预期结果以总纲对应编号及架构合同为准。ARCH 项是工程交付门禁，不表示已有实现或测试。现有竞品能力、旧项目演示、历史测试和文档自检，均不能直接证明本项目通过。

## 一、<span id="acceptance-rules">验收口径</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

### 1.1、<span id="acceptance-status">状态与证据</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 状态 | 使用条件 |
| --- | --- |
| 通过 | 在明确的交付版本和适用范围内，所有验收条件满足，且证据可定位、可复核 |
| 存疑 | 已执行验证，但结果冲突、证据不完整或仍有未闭合问题；不计为通过 |
| 不通过 | 已执行验证，确认不满足至少一项适用的验收条件；记录失败、影响与复测入口 |
| 未验收 | 尚未验证、证据已失效或验证范围尚未完整；不得以代码存在替代验收 |
| 不适用 | 发布范围明确排除且有范围决策记录；说明原因、适用边界与批准记录 |

“证据/备注”必须记录交付版本、阶段与能力清单版本、环境和服务拓扑、客户端/系统版本、执行人/日期、用例与结果、日志/录屏/报告链接及遗留问题；涉及多个平台或版本时，可在本行链接分平台明细。证据文件使用相对路径，敏感凭据和聊天正文先脱敏。

性能和可用性验收在执行前锁定指标起止点、负载包络、阈值、分位数/统计窗口、错误预算、样本量与观测方式。在线接受/收讫、离线补同步、删除截止后的实际清理滞后分别记录；测完再改阈值或只返回接口成功不能作为通过证据，具体覆盖 T-43 与 ARCH-22。

需求所含的成功、失败、异常、权限和跨端状态均属于验收范围。只有部分平台或部分子项通过时，本编号不能标为全量通过。主状态应反映当前适用范围整体结果，分平台结论写入证据明细。

### 1.2、<span id="acceptance-validity">范围与证据有效期</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

源码、依赖、协议、接口、配置、部署拓扑、系统适配或验收条件发生影响行为的变更时，相关结论必须重新评估。原证据无法覆盖当前版本时，将该项重置为“未验收”，保留旧记录并链接新的回归范围。

需求编号沿用总纲；不要因拆分任务或调整顺序重编号。新增子项可挂在编号下的证据文件中，不能删除主台账行。适用范围按 [三阶段目标](../IM需求明细表.md/IM需求明细表.md#phase-goals) 与服务端能力清单确定，同时记录终端、部署配置、角色和业务场景。后续阶段尚未实现的功能保持“未验收”；某期未启用不等于全量产品永久“不适用”，不能靠关闭能力回避该期必需项。

通信分类按 [图解](../IM通信方式图解.md/IM通信方式图解.md) 记录中心化／去中心化，以及实际网络、通道、身份和支持端。去中心化候选不自动继承中心化云历史、管理员权限、删除或灾备证据；蓝牙／附近 Wi-Fi 未选定实现，不能列为基础五端已通过。`network.endpoint_group_failover` 仅高级验组轮询／动态及发版更新，基础／标准验证模块不初始化且固定入口正常重连；图文校验不代替连接、消息和恢复实测。

### 1.3、<span id="phase-gates">三阶段验收与封版</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

| 阶段 | 验收范围 | 完成门禁 |
| --- | --- | --- |
| 一阶段：基础版 | 主营内核为可靠纯文本单聊；CLI 与四图形端基础互通，邮箱注册/绑定/OTP、核心安全治理、Redis、独立微服务部署、最小 SDK/业务中间件及该期明确能力；具备后台可配置收讫删除与删除回调合同 | 五端纯文本收发、离线补同步和权限一致性通过；T-56～58/ARCH-35生产灾备适用项通过；图片/媒体/文件/群等越级消息由服务端拒绝，未启扩展不初始化；基础适用项全部通过、证据完整、阻塞问题清零，才可形成基础封版记录 |
| 二阶段：标准版 | 继承基础全部责任；主营内核增加图片（静态/动图）、音频/视频消息、文件及群聊天；音视频消息与实时音视频通话独立验收，其余已确认周边按本期范围交付 | 完整消息类型及群成员/权限/历史合同通过，消息置顶、@ 群成员、消息收藏等高级能力在标准预设关闭；新增项通过并重跑受影响基础项，不得以新增功能覆盖基础回归 |
| 三阶段：高级版 | 继承标准全部责任；主营内核增加阅后即焚、独立加密模块及可切换协议，增加消息置顶、@ 群成员、消息收藏等体验增强；转账及配套个人账单、后台对账属于高级资金能力，其他特殊场景按需启用 | 验证隐私生命周期、协议协商/切换与旧密文读取、体验增强权限/同步；开启资金必须同时通过[转账与账单专项](#money-acceptance-cases)，不能只验聊天卡片；新增项通过并完成基础/标准受影响回归、插件隔离和安全边界验收 |

封版须冻结可重建的源码标识、接口/事件合同、数据库与迁移版本、确切依赖和许可证清单、服务配置、能力清单、部署说明及逐项证据。封版后的修复形成新版本，保留原基线并验证影响范围；当前文档建立不表示已经封版。二、三阶段在同一产品工程中增量继承，产品阶段、部署能力组合与会员等级分别记录。CLI 可以先打通链路，但只有 CLI 通过不能代表完整基础版封版。

基础各标段先完成自身证据，再完成跨标段和五端集成验收。非后端人员独立部署、运行、诊断和反部署是基础封版门禁，具体见 T-44～46、ARCH-33；不能以作者机器的手工部署、旧项目测试或容器 Running 状态代替。

前端工程按[独立前端架构](../IM前端架构表.md/IM前端架构表.md#frontend-scope)交付；T-47 核对本地事务、同步与数据隔离，T-48 核对全新独立 <u>[**Swift**](https://www.swift.org/)</u> 工程的模板组织、依赖安装、真实构建与签名产物，ARCH-34 核对整体交付。模板和依赖安装成功不能替代 IM 业务运行证据；[**SQLite**](https://sqlite.org/) 引擎已确认，存储封装与各端具体工具链按锁定记录验收，选型已确定，真实安装/构建/运行证据由Codex补齐，不得把选型记录当作验收通过。

每期发布报告列出本期适用编号集合与排除理由；不要求一阶段完成三阶段全部能力，也不能把尚未验证的后续项统计为“通过”。

主营消息内核是每阶段必需验收门禁，周边模块的完成情况不能替代它。基础 → 标准 → 高级的继承回归覆盖发送、接收、离线、多设备、权限、删除和故障恢复；每次升档、降档或变更预设同时验证 UI 展示和直接 API 调用。基础纯文本可以包含 Unicode 表情字符；基础安全中的传输/存储加密不等于高级 E2EE。高级消息置顶与用户个人会话排序置顶分别验收。细化证据落在 T-26～43、ARCH-03/06/07/08/10/22/25～32，按阶段、子能力与实际平台核对适用范围，不能将旧端无法处理的类型强行转换为普通文本。

工程基线 `IM-baseline-20261008.2` 已由 Codex 选择具体版本、最低系统、存储访问层、默认参数、硬件/SLO、E2EE和自有源码许可，详见[前端版本](../IM前端架构表.md/IM前端架构表.md#frontend-locks)、[后端默认值](../IM后端架构表.md/IM后端架构表.md#operational-defaults)、[硬件与测试](../IM后端架构表.md/IM后端架构表.md#hardware-baseline)及[密码/许可合同](../IM后端架构表.md/IM后端架构表.md#crypto-providers)。Codex 负责生成真实lock/摘要、实现兼容、脚本与压测/安全/恢复证据并整改；Jobs负责产品目标与体验反馈。**已选工程决策不等于验收通过**，缺代码或证据的243项继续保持未验收，不要求用户补技术判断。

### 5.1、<span id="money-acceptance-cases">转账与账单专项验收</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

以下是 FE-089／FE-090／BE-028／T-14 的高级资金子场景，不增加主台账编号，当前均未执行验收。开启任一真实资金业务必须配套个人账单和后台对账；积分、链上交易和普通 IM 转账分别验证，不能相互替代。真实渠道尚未获权或未完成上线条件时，只验证隔离模拟环境，不真实动钱，不将模拟结果记为真实渠道已通过。

默认产品合同为 **同一作用域内不同 IM 账户间、同币种可用余额转账，收款方确认后到账**；不允许自己转给自己。发起时预留余额，待收款默认 **24 小时**，后台可配置并在订单发起时固定截止，修改默认不追改旧单。手续费默认 **0**；配置收费时固定付款方／收款方承担方式，预留涵盖付款方总扣款，收款方净到账必须大于0。未提交的表单／意图可取消；`transfer.sender_cancel_pending` 默认 `false`，拒绝发送方单方撤销待收款，启用后只允许原发送方取消尚未收款的订单，与收款／拒收／到期竞争唯一结果；已结算纠错通过退款／冲正，不依赖聊天卡片撤回。具体行为和工程合同见[转账与账单需求](../IM需求明细表.md/IM需求明细表.md#transfer-billing)、[端侧资金交互](../IM前端架构表.md/IM前端架构表.md#money-client-contract)和[转账／账本／对账架构](../IM后端架构表.md/IM后端架构表.md#money-transfer-billing)。
